This document describes how Eskiu's documentation is organized and how to maintain it.

## Document Categories

### Root-Level (Quick Reference)

These 4 files are at the project root for quick access:

1. **README.md** — Project overview, why Eskiu, 5-minute example
2. **QUICKSTART.md** — Fastest path to first compilation
3. **RELEASES.md** — Version history, what's new, what's fixed
4. **INDEX.md** — Navigation hub to all documentation

**Maintenance:** Update RELEASES.md with every significant change. Keep README.md and QUICKSTART.md examples accurate and current.

### Getting Started (docs/)

For new users learning the language:

1. **GETTING_STARTED.md** — Complete tutorial with examples
2. **BUILD.md** — Installation for all platforms
3. **DEBUGGING.md** — Test modes and troubleshooting

**Maintenance:** Keep syntax examples in C-style (not Rust-style). Test examples regularly.

### Language Reference (docs/)

Complete specifications for programmers:

1. **LANGUAGE_SPEC.md** — Full syntax, types, operators
2. **GLOSSARY.md** — All technical terms defined
3. **FAQ.md** — Common questions and answers

**Maintenance:** Update LANGUAGE_SPEC.md when syntax changes. Add to GLOSSARY.md for new features.

### Architecture & Development (docs/)

For compiler developers and contributors:

1. **ARCHITECTURE.md** — Compiler phases, design
2. **DESIGN_DECISIONS.md** — Why certain language choices
3. **PERFORMANCE.md** — Profiling and optimization
4. **CONTRIBUTING.md** — How to contribute to Eskiu
5. **PHASES.md** — Development roadmap
6. **API.md** — C++ API for embedders
7. **REFACTORING.md** — Major refactors and changes

**Maintenance:** Update REFACTORING.md when making architectural changes. Update PHASES.md when roadmap changes.

## Maintenance Guidelines

### When Adding a New Feature

1. Update **LANGUAGE_SPEC.md** with syntax
2. Add example to **GETTING_STARTED.md**
3. Update **GLOSSARY.md** if new terms introduced
4. Document in **ARCHITECTURE.md** if it affects compiler design
5. Add FAQ entries if likely to confuse users

### When Fixing a Bug

1. Update **RELEASES.md** under "Bug Fixes"
2. Update **DEBUGGING.md** if it affects troubleshooting
3. Add to **FAQ.md** if it's a common issue

### When Refactoring Code

1. Create entry in **REFACTORING.md**
2. Update **ARCHITECTURE.md** if design changes
3. Update **DESIGN_DECISIONS.md** if rationale changes
4. Document C++ changes in **API.md** if public API affected

### When Updating Build Process

1. Update **BUILD.md** with new steps
2. Update **DEBUGGING.md** if test modes change
3. Update **CONTRIBUTING.md** if developer setup changes

## Documentation Style Guidelines

### Writing Style

- **Clear & Concise:** Avoid unnecessary jargon. Explain acronyms on first use.
- **Active Voice:** "The parser generates an AST" not "An AST is generated by the parser"
- **Examples:** Every major concept should have a code example
- **Links:** Cross-reference related documents

### Code Examples

- **Format:** Use triple backticks with language identifier
  ````
  ```esk
  i32 x = 5;  // C-style syntax
  ```
  ````
- **Correctness:** All examples must compile and run
- **Style:** Use current C-style syntax (not Rust-style)

### Headings

- Use `#` for document title (only one per file)
- Use `##` for major sections
- Use `###` for subsections
- Use `####` for sub-subsections (rarely needed)

### Tables

Use markdown tables for structured information:
```markdown
| Column 1 | Column 2 | Column 3 |
|----------|----------|----------|
| Data     | Data     | Data     |
```

## Consolidation & Cleanup

### Temporary Documentation

Do not commit temporary documentation files to root:
- ❌ REFACTOR_SUMMARY.md (use docs/REFACTORING.md instead)
- ❌ PARSER_FIX.md (consolidate into main docs)
- ❌ SYNTAX_CLARIFICATION.md (put in GETTING_STARTED.md or LANGUAGE_SPEC.md)

**Rule:** If it's not long-term reference material, consolidate it into one of the permanent documents.

### Deprecation

When a document is deprecated:
1. Mark it clearly with `# ⚠️ DEPRECATED`
2. Link to the replacement document
3. Keep it in repo for a few releases, then remove

Example:
```markdown
# ⚠️ DEPRECATED — Use [docs/BUILD.md](docs/BUILD.md) instead

This document is deprecated. See [BUILD.md](../docs/BUILD.md) for current instructions.
```

Before merging documentation changes:
- [ ] Examples compile and run correctly
- [ ] C-style syntax used (not Rust-style)
- [ ] Links to other docs work correctly
- [ ] Headings are properly structured
- [ ] Spelling and grammar checked
